# Product Requirements Document: Family Access Control System

**Version**: 1.2  
**Date**: May 9, 2026  
**Status**: Draft - Updated with OAuth and Legacy Username/Password Support  
**Last Updated**: May 9, 2026

---

## 1. Executive Summary

This PRD outlines a redesigned family access control system for KakiLogger that enables:
- Family members to have their own user accounts with multiple authentication methods
- Support for legacy username/password, modern email/password, Google Sign-In, and Apple Sign-In
- Role-based access control (Adult/Child roles)
- Adults to manage their own logs and view their children's logs
- Children to view and manage only their own logs
- Clear compartmentalization of data based on user role and relationship
- Seamless account linking between different authentication methods

---

## 2. Problem Statement

**Current State:**
- Only the primary user can log in
- Family members exist but cannot access the app independently
- No role-based access control
- No parent-child relationship management

**Desired State:**
- Each family member can have their own account
- Clear access rules based on user role (Adult/Child)
- Parents/Guardians can monitor children's health data
- Children can independently log their own data

---

## 3. Goals & Objectives

1. **Enable family member independence**: Allow each family member to log in with their own credentials
2. **Implement role-based access**: Distinguish between adult and child users
3. **Establish data compartmentalization**: Control what data each user can view/edit
4. **Maintain family visibility**: Adults can view all family members' logs
5. **Protect child data**: Children can only view their own logs

---

## 4. User Types & Roles

### 4.1 User Roles

#### **Adult (Parent/Guardian)**
- Can create a personal account
- Can create child accounts (children's profile)
- Can log their own stool data
- Can view their own logs, charts, and statistics
- Can view all children's logs, charts, and statistics
- Can manage family member profiles
- Can set up child accounts or approve child self-registration

#### **Child**
- Can create their own account (with parent approval or using family code)
- Can log their own stool data
- Can view only their own logs, charts, and statistics
- Cannot view other family members' data
- Cannot manage family members

## 5. Core Features

### 5.1 Authentication & Account Management

**Feature 5.1.1: Adult User Registration & Login**
- Register/Login with multiple methods:
  - Username/Password (traditional, original method)
  - Email/Password (traditional, email-based method)
  - Google Sign-In (OAuth 2.0)
  - Apple Sign-In (OAuth 2.0)
- Email confirmation (for email/password method only)
- Set up initial family profile (themselves as primary user)
- Support for both legacy username-based and modern email-based authentication

**Feature 5.1.1a: Traditional Username/Password Login**
- Adults can register with username and password
- Login with username and password (legacy method)
- No email requirement for this method
- Password reset via registered email (optional)
- Backward compatible with existing accounts

**Feature 5.1.1b: Traditional Email/Password Login**
- Adults can register with email and password
- Login with email and password (modern method)
- Email confirmation required
- Password reset via email link
- Can coexist with username/password accounts

**Feature 5.1.1c: Google Sign-In**
- Adults can sign up/login using Google account
- OAuth flow handles authentication
- Auto-populates name from Google profile
- Links Google account to KakiLogger account
- One-click login on subsequent visits
- Works across all devices

**Feature 5.1.1d: Apple Sign-In**
- Adults can sign up/login using Apple ID
- OAuth flow handles authentication
- Auto-populates name from Apple profile
- Links Apple account to KakiLogger account
- One-click login on subsequent visits
- Privacy-focused (Hide My Email option supported)
- Required for iOS/macOS app distribution

**Feature 5.1.2: Child User Registration**
- Option A: Parent creates child account with:
  - Child's name
  - Child's age/DOB
  - Temporary password (parent sets)
- Option B: Child self-registers with:
  - Family invite code (generated by parent)
  - Child's name
  - Temporary password
- Note: OAuth (Google/Apple) not available for child accounts for security/parental control reasons

**Feature 5.1.3: Family Code/Invite System**
- Adults can generate unique family invite codes
- Codes are time-limited (e.g., 30 days)
- Codes can be revoked/regenerated
- Children can use codes to join family

### 5.2 Access Control

**Feature 5.2.1: Role-Based View Access**
- Admin endpoint: `GET /api/logs` filters based on user role
  - Adult: Returns user's logs + all children's logs
  - Child: Returns only user's own logs

**Feature 5.2.2: Data Compartmentalization**
- Calendar view shows only accessible logs
- Charts show only accessible logs
- Statistics calculated only from accessible data
- Export/Share features respect role restrictions

**Feature 5.2.3: Family Member Selector**
- Adults see dropdown to view specific family member's data
- Switching between "My Logs" and "Child Name's Logs"
- Charts/Stats update based on selected member

### 5.3 Family Management

**Feature 5.3.1: Family Member Management (Admin Panel)**
- View all family members (name, role, age)
- Edit family member details (name, age)
- Deactivate/remove family members
- Set user roles (Adult/Child)

**Feature 5.3.2: Family Relationships**
- Define relationships: "Parent", "Sibling", "Grandparent", etc.
- Currently only care about Adult vs Child for access
- Future: enable peer access (siblings can view each other)

## 6. User Workflows

### 6.1 Workflow: Adult Registers with Username/Password (Legacy)

```
1. Adult visits login page
   - Clicks "Sign in with Username" or login form
   - Enters username and password
   - Login succeeds or fails based on credentials
   - Logged in with existing legacy account

2. Adult creates child account
   - Fills: Child name, age/DOB
   - Sets temporary password or generates invite code
   - Child can now log in

3. Adult views dashboard
   - Sees toggle/dropdown: "My Logs" vs "Child's Logs"
   - Can view both their logs and child's logs
   - Can manage family settings
```

### 6.1b Workflow: Adult Registers with Email/Password (Modern)

```
1. Adult visits login page
   - Clicks "Sign up" or "Register"
   - Enters email and password
   - Confirms email address via link
   - Account created and logged in

2. Adult creates child account
   - Fills: Child name, age/DOB
   - Sets temporary password or generates invite code
   - Child can now log in

3. Adult views dashboard
   - Sees toggle/dropdown: "My Logs" vs "Child's Logs"
   - Can view both their logs and child's logs
   - Can manage family settings
```

### 6.1c Workflow: Adult Registers with Google Sign-In

```
1. Adult visits login page
   - Clicks "Sign in with Google" button
   - Redirected to Google consent screen
   - Approves scope permissions (email, profile)
   - Redirected back to KakiLogger
   - Account auto-created or existing account linked
   - Logged in immediately

2. Adult creates child account
   - Same as workflow 6.1 step 2

3. On next login
   - Clicks "Sign in with Google"
   - No password needed
   - One-click login
```

### 6.1c Workflow: Adult Registers with Apple Sign-In

```
1. Adult visits login page
   - Clicks "Sign in with Apple" button (especially on iOS/Safari)
   - Redirected to Apple authentication
   - Approves to sign in
   - Option to hide email address (privacy feature)
   - Redirected back to KakiLogger
   - Account auto-created or existing account linked
   - Logged in immediately

2. Adult creates child account
   - Same as workflow 6.1 step 2

3. On next login
   - Clicks "Sign in with Apple"
   - Biometric/device authentication
   - One-click login
```

### 6.2 Workflow: Child Self-Registers with Invite Code

```
1. Adult (registered via email, Google, or Apple) generates invite code in settings
   - Code has 30-day expiration
   - Shares code with child

2. Child visits app
   - Clicks "Join Family" (if not logged in)
   - Enters invite code
   - Creates account (name, password)
   - Account created as "Child" role

3. Child logs in
   - Sees only their own logs
   - Can add new logs
   - Can view their charts/stats
```

### 6.3 Workflow: Adult Views Child's Data

```
1. Adult logs in (via email/password, Google, or Apple)
2. Sees "Family Member Selector" (dropdown/tabs)
   - Options: "My Logs", "Child Name", "Another Child"
3. Selects child
   - Calendar shows child's logs
   - Charts display child's data
   - Can add logs on behalf of child (optional)
4. Returns to own logs
   - Selector shows own data again
```

## 9. API Changes

### 9.1 New Endpoints

**POST /api/auth/register**
- Create new user account with multiple methods:
  - Username/Password (legacy - username + password only)
  - Email/Password (modern - email + password with confirmation)
  - Google OAuth (auto-account creation)
  - Apple OAuth (auto-account creation)
- Validate credentials based on auth method
- Return user info + role
- Set session/JWT token

**POST /api/auth/login**
- Authenticate user with supported methods:
  - Username/Password (legacy method)
  - Email/Password (modern method)
- Return user info + role
- Return accessible family members list
- Set session/JWT token
- Support for both legacy and modern credential types

**POST /api/auth/google/callback**
- Handle Google OAuth callback
- Exchange authorization code for access token
- Create or link Google account to user
- Auto-populate name from Google profile
- Return user info + role
- Set session/JWT token
- If new user, create account with "adult" role
- If existing user with different email, ask for merge confirmation

**POST /api/auth/apple/callback**
- Handle Apple OAuth callback
- Exchange authorization code for access token
- Create or link Apple account to user
- Auto-populate name from Apple profile
- Return user info + role
- Set session/JWT token
- If new user, create account with "adult" role
- Handle "Hide My Email" feature (email relay)

**GET /api/auth/google/login**
- Redirect to Google OAuth consent screen
- Pass client ID, scopes, redirect URI
- Scopes: openid, profile, email

**GET /api/auth/apple/login**
- Redirect to Apple OAuth consent screen
- Pass client ID, scopes, redirect URI, team ID
- Scopes: name, email, email_verified

**POST /api/auth/logout**
- Clear session/JWT token
- Invalidate refresh tokens
- Redirect to login page

**POST /api/auth/link-oauth**
- Link additional OAuth provider to existing account
- User must be logged in
- Validate OAuth provider response
- Add to authMethods array
- Prevent duplicate provider linkage

**POST /api/auth/unlink-oauth**
- Unlink OAuth provider from account
- Validate user has at least one auth method remaining
- Return error if last auth method

**GET /api/auth/me**
- Return current logged-in user info
- Include authMethods array
- Include linked OAuth providers
- Return accessible family members

**GET /api/family/invite-codes**
- List active invite codes for logged-in adult
- Show usage status

**POST /api/family/invite-codes**
- Generate new invite code
- Set expiration

**DELETE /api/family/invite-codes/:code**
- Revoke invite code

**GET /api/family/members**
- List all family members for logged-in user
- Return full details if adult, limited if child

**PATCH /api/family/members/:id**
- Edit family member details (adult only)

### 9.2 Modified Endpoints

**GET /api/logs**
- Add query param: `?memberId=xyz` or `?familyMemberId=xyz`
- Filter based on user role:
  - Adult: Return own logs + specified child's logs
  - Child: Return only own logs (ignore memberId param)

**GET /api/logs?memberId=current**
- Return logs for currently logged-in user

**POST /api/log**
- Verify user can log for the date/member combination
- Adults can log for themselves or children
- Children can only log for themselves

**DELETE /api/log/:id**
- Verify user can delete this log
- Check role + ownership

## 9.3 OAuth Configuration & Implementation

### 9.3.1 Google Sign-In Setup

**Configuration:**
- Create OAuth 2.0 credentials in Google Cloud Console
- Get Client ID and Client Secret
- Set Authorized Redirect URIs: `https://kakilogger.com/api/auth/google/callback`
- Store credentials in environment variables: `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`

**Frontend Implementation:**
- Use `@react-oauth/google` library for Google Sign-In button
- Button shows "Sign in with Google"
- Handles consent flow and token exchange
- Sends ID token to backend

**Backend Implementation:**
- Verify ID token with Google's public keys
- Extract user info: email, name, picture, sub (Google ID)
- Check if user exists by googleId
- If exists: log in, update lastLogin
- If not exists: create new adult account, set googleId
- Store idToken and refreshToken securely
- Create session/JWT token for app

**Security:**
- Verify token signature before accepting
- Validate token expiration
- Store refresh tokens in secure HttpOnly cookies
- Implement CSRF protection for OAuth flow

### 9.3.2 Apple Sign-In Setup

**Configuration:**
- Create App ID in Apple Developer Account
- Enable "Sign In with Apple" capability
- Create OAuth credentials with Team ID
- Get Client ID (Service ID) and Client Secret
- Set Return URLs: `https://kakilogger.com/api/auth/apple/callback`
- Store credentials in environment variables: `APPLE_CLIENT_ID`, `APPLE_TEAM_ID`, `APPLE_KEY_ID`, `APPLE_PRIVATE_KEY`

**Frontend Implementation:**
- Use `apple-sign-in-button` or native implementation
- Button shows "Sign in with Apple"
- User authenticates with Apple ID (Face ID, Touch ID, or password)
- User can choose to hide email (privacy feature)
- Browser returns identity token and authorization code

**Backend Implementation:**
- Verify JWT with Apple's public keys
- Extract user info: email, name, iss, sub (Apple ID)
- Handle hidden email scenario (email relay: user@privaterelay.appleid.com)
- Check if user exists by appleId
- If exists: log in, update lastLogin
- If not exists: create new adult account, set appleId
- On first sign-in, Apple provides user's name (subsequent sign-ins don't)
- Store and refresh tokens securely

**Special Handling:**
- First-time Apple sign-in provides: name, email, real_user_status
- Subsequent sign-ins only provide: email, real_user_status
- Handle case where user email is hidden (privaterelay)
- Validate `real_user_status` to prevent bot accounts

**Security:**
- Verify JWT signature before accepting
- Validate token expiration and aud (app identifier)
- Store refresh tokens in secure HttpOnly cookies
- Implement CSRF protection for OAuth flow
- Validate real_user_status to ensure human user

### 9.3.3 Session & Token Management

**Session Strategy:**
- Use JWT tokens with 1-hour expiration
- Refresh tokens with 30-day expiration stored in HttpOnly cookies
- Include user ID, role, familyId in JWT payload
- Verify JWT on every protected API call

**Token Refresh:**
- POST /api/auth/refresh to get new JWT
- Validate refresh token
- Return new JWT
- Rotate refresh token on each refresh (optional security enhancement)

**Logout:**
- Clear JWT from localStorage (client)
- Clear refresh token cookie (server)
- Invalidate any active sessions

### 9.3.4 Account Linking

**Scenario: User logs in with Google, then later tries to sign in with Apple**
- Check if Google email matches Apple email
- If emails match, offer to link accounts
- Confirm user identity before linking
- Add new OAuth method to authMethods array
- User can now sign in with either method

**Duplicate Account Prevention:**
- Query by googleId, appleId, and email
- On OAuth login, check all fields to detect existing accounts
- Suggest account linking if email matches

## 11. Security & Privacy Considerations

### 11.1 Data Isolation
- Users can only access data they own or are authorized to access
- Database queries must filter by familyId + userId/role
- Client-side filtering is insufficient; API must enforce

### 11.2 Password Security
- Hash passwords with bcrypt/pbkdf2 (continue current approach)
- Enforce minimum password complexity
- Implement password reset flow for forgotten passwords

### 11.3 Invite Code Security
- Generate cryptographically random codes
- Codes are single-use or time-limited
- Rate-limit code generation to prevent abuse
- Log invite code usage for audit trail

### 11.4 Session Management
- Session tokens (if applicable) scoped to user
- Clear user role in token for authorization checks
- Logout clears session/token
- JWT tokens include expiration and refresh mechanism
- HttpOnly cookies prevent XSS access to tokens

### 11.5 OAuth Security
- Use HTTPS for all OAuth flows
- Implement CSRF protection (state parameter)
- Verify OAuth provider signatures before accepting tokens
- Store OAuth secrets in environment variables (never commit to code)
- Validate redirect URIs match registered URIs exactly
- Never trust client_id alone; always verify with client_secret on backend
- Use secure randomization for state tokens
- Rate-limit OAuth callback endpoints to prevent abuse
- Log all OAuth authentication attempts for audit trail
- Store refresh tokens securely (HttpOnly cookies only)

### 11.6 Data Privacy
- Parents have access to children's health data
- Children do not have access to parents' health data
- Consider GDPR/privacy regulations for children's data

## 15. Risks & Mitigation

| Risk | Impact | Mitigation |
|------|--------|-----------|
| Data leakage between families | High | Implement strong DB filters, comprehensive testing |
| Children accessing adult data | High | Role-based checks on all API endpoints |
| OAuth token compromise | High | Use HTTPS, secure token storage, token rotation |
| Account linking confusion | Medium | Clear UI indicators, email verification |
| Invite code abuse | Medium | Rate limiting, expiration, audit logs |
| UX confusion (which member?) | Medium | Clear UI indicators, member selector prominence |
| OAuth provider downtime | Medium | Fallback to email/password, graceful degradation |
| Duplicate accounts via different OAuth | Medium | Email verification, account linking suggestions |
| Migration issues for existing users | Medium | Careful schema migration, data validation |
| CSRF attacks on OAuth flow | Medium | State parameter, HTTPS only, SameSite cookies |

## 17. Questions & Open Items

1. **Age of Consent**: At what age can a child's account become independent (no parent oversight)?
2. **Child to Adult Migration**: Can a child account be converted to adult when they reach age 18?
3. **Parental Consent**: Should app require explicit parental consent before child can log in?
4. **Editing Permissions**: Can adults edit child logs, or only children?
5. **Family Code Sharing**: Should there be a family code for multiple children to join, or individual codes?
6. **Account Recovery**: How should children recover forgotten passwords? (Email or parent?)
7. **OAuth Email Hiding**: Should we support Apple's "Hide My Email" feature?
8. **Account Merging**: If a user creates account with username/email/OAuth and tries another method with same email, should we auto-merge or ask?
9. **OAuth Failure Fallback**: What should happen if OAuth provider is down? (e.g., Google servers unavailable)
10. **Child OAuth**: Should children ever be allowed to use OAuth (Google/Apple) sign-in for security/control reasons?
11. **Legacy Username Support**: How long should we maintain support for username/password-only accounts? (Migration timeline)
12. **Username Uniqueness**: Should usernames be globally unique or only unique within families?
13. **Username to Email Migration**: Should we offer existing username-only users a path to add email authentication?
